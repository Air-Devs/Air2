## 二、1.7.10（KW）排障现状 —— 已锁定根因方向

真机 hs_err（`hs_err_pid8962.log`）的栈是决定性的：

```
C  [libGLESv2] gl::GLES1State::loadMatrix(...)
j  org.lwjgl.opengl.GL11.glLoadIdentity()
j  bmg.c → bao.aj → … → net.minecraft.client.main.Main.main
```

**结论：MC 的 GL 调用经 lwjglx 落到 LWJGL 的 GLES 绑定，而 GLES 绑定默认库名是 `libGLESv2`（ANGLE）**，所以：
- 我们改 `opengl.libname` 无效（那是桌面 GL 的库名）
- KW 从未被调用（0 条 `[A2-GL-STUB]`、解析器拒绝计数 1、桩调用 0）
- 换 b13 的 KW 二进制、RTLD_LOCAL、删 ANGLE 都不能解决（删 ANGLE 会让 libEGL 自己崩）

**下一步（第一件事）**：~~验证 `56c78e6`~~ —— **已验证，无效**（见下）。

### 追加结论：`56c78e6`（opengles.libname）无效
- 真机 lastlog-90：`opengl.libname=nggl4es_kw opengles.libname=nggl4es_kw` 两条都生效
- 但仍崩：hs_err_pid9028 的栈与之前完全一致（`GL11.glLoadIdentity()` → `libGLESv2` → `GLES1State::loadMatrix`）
- 全包扫描：**没有任何 jar 写死 `GLESv2`**，只有 GL 原生库（KW/gl4es/MG/ANGLE）引用它
- ⇒ 结论：**LWJGL 的 GL11 原生绑定并不按这两个属性加载**，它自己用了 `libGLESv2`

**下周第一件事**：用 LLDB 在设备上对 `glLoadIdentity` 下断点，确认命中的是哪张镜像（哪个 dylib），再决定改绑定还是换提供者。不要再改启动参数。

## 六、追加结论：KW 白名单也无效（`c588439`）

真机 lastlog-95：
```
 [A2-GL-WL] KW 非 ES3 入口 ⇒ 空桩：glLoadMatrixf     ← 拦到了（只有这一个名字）
 但崩溃照旧：gl::GLES1State::loadMatrix ← gl::ContextPrivateLoadIdentity
```
⇒ 我们给 KW 的是空桩，ANGLE 那段代码仍被执行 ⇒ **触发它的不是经我们解析器的那次调用**。

**关于 LWJGL 的一个重要事实（lastlog-93 已证）**：
```
 opengl provider .library = MacOSXLibraryDL [0x39AB510B0] ← 正是 KW 的 handle
 org.lwjgl.opengles.GLES 类根本不存在（ClassNotFoundException）
```
⇒ 绑定没错；`opengles.libname` 是无效参数（`56c78e6` 已验证无效）。

**关于 KW 二进制的两个事实**：
```
 otool -L：只依赖 @rpath/libnggl4es.dylib，**不链 libGLESv2**
 符号面：有 glLoadIdentity/glMatrixMode，无 dlopen、无 eglGetProcAddress
```
